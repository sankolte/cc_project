# 🚨 Cloud-Based Web Application Monitoring & Anomaly Detection System

> A cloud-based monitoring platform that collects logs generated by a web application, processes them asynchronously using AWS services, analyzes application behaviour, detects anomalies, and presents system health and incidents through a monitoring dashboard.

---

# 📌 1. Project Overview

Modern web applications continuously generate operational data.

For example, whenever a user logs into a website, searches for a product, places an order, or calls an API, the backend generates information such as:

```
Request received
Endpoint: /products
Method: GET
Status: 200
Latency: 143 ms
```

Similarly, when something goes wrong:

```
Endpoint: /payment
Status: 500
Latency: 2400 ms
Error: Database timeout
```

In a real-world application, thousands or millions of such events can be generated.

Simply storing these logs is not enough.

Developers also need to know:

* Is the application healthy?
* Which API is failing?
* Has the error rate suddenly increased?
* Is an API becoming slower?
* Is there an unusual increase in traffic?
* Are there an abnormal number of failed login attempts?
* When did the problem start?
* How severe is the problem?

### Our project addresses this problem.

We will build **two connected systems**:

### 1. Target Web Application

A small web-based application that represents a real-world application.

For example, an e-commerce application called:

> **ShopPulse**

It will contain APIs such as:

```text
POST /login
GET  /products
GET  /products/:id
POST /cart
POST /orders
POST /payment
GET  /orders/:id
```

The application will generate logs whenever these APIs are used.

---

### 2. Cloud Monitoring System

A separate cloud-based system will collect and process the logs generated by ShopPulse.

The monitoring system will:

```text
Collect Logs
     ↓
Queue Logs
     ↓
Process Logs
     ↓
Store Logs
     ↓
Calculate Metrics
     ↓
Detect Anomalies
     ↓
Generate Incidents
     ↓
Display Dashboard
```

# 🎯 3. Problem Statement

Web applications generate a large amount of operational data.

When the number of requests increases, manually checking logs becomes difficult.

A small error may be hidden among thousands of successful requests.

For example:

```text
200 OK
200 OK
200 OK
200 OK
500 ERROR
200 OK
200 OK
500 ERROR
200 OK
...
```

If the application receives 100,000 requests, manually identifying abnormal behaviour is impractical.

Therefore, we need a system that can:

1. Collect application logs.
2. Process them automatically.
3. Calculate meaningful metrics.
4. Compare current behaviour with normal behaviour.
5. Detect abnormal patterns.
6. Display those abnormalities to developers.

# 📬 13. Why Amazon SQS?

One of the most important architectural decisions is using **Amazon SQS**.

We don't want the backend to do everything synchronously.

Without SQS:

```text
Application
     ↓
Backend
     ↓
Process Log
     ↓
Store Log
     ↓
Analyze Log
```

If thousands of logs arrive simultaneously, the backend could become overloaded.

Instead:

```text
Application
     ↓
Backend
     ↓
SQS
     ↓
Workers
```

The queue acts as a buffer.

---

## Benefits

### Decoupling

The API and processing worker are independent.

### Buffering

Large numbers of logs can wait in the queue.

### Reliability

Messages can be retried when processing fails.

### Scalability

Multiple workers can process messages simultaneously.

```text
                SQS
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Worker 1  Worker 2  Worker 3
```

---

# 🧠 19. Establishing Normal Behaviour

The anomaly detector needs to understand:

> "What is normal?"

Therefore, initially we generate normal traffic.

For example:

```text
1000 requests/min
Error rate ≈ 1.5%
Average latency ≈ 150ms
```

This becomes our **baseline**.

Then we introduce abnormal behaviour.

Example:

```text
Error rate → 28%
Latency → 2500ms
```

The system compares:

```text
Current Behaviour
       VS
Normal Baseline
```

and identifies an anomaly.

---

# 📐 20. Anomaly Detection Methods

We can implement anomaly detection progressively.

## Level 1 — Threshold Based

The simplest method.

Example:

```text
IF error_rate > 10%
    → HIGH ERROR ANOMALY
```

and:

```text
IF average_latency > 2000ms
    → HIGH LATENCY ANOMALY
```

This is simple and reliable for controlled demonstration scenarios.

---

# 📊 Level 2 — Statistical Detection

A more advanced implementation can use statistical methods.

For example, Z-score:

```text
z = (x - μ) / σ
```

Where:

* `x` = current value
* `μ` = historical mean
* `σ` = standard deviation

If:

```text
|z| > 3
```

the value can be considered significantly unusual.

This can make the anomaly detection component more interesting from a technical perspective.

We will use IAM roles and policies to control access to AWS resources.

For example:


The worker should receive only the permissions it actually needs.

This follows the:

> **Principle of Least Privilege**

# ☠️ 32. Dead Letter Queue

A Dead Letter Queue can be configured for messages that repeatedly fail.

```text
             SQS
              │
              ▼
           Worker
              │
        ┌─────┴─────┐
        │           │
     Success      Failure
        │           │
        ▼           ▼
       Done       Retry
                    │
                    ▼
             Repeated Failure
                    │
                    ▼
                   DLQ
```

This is an optional advanced feature but would strengthen the cloud architecture.

# 💭 46. In Simple Words

Agar poore project ko ekdum simple language mein explain karna ho:

> **Hum ek simple web application banayenge, maan lo e-commerce application. Us application par users ke requests aayenge aur usse logs generate honge. Hum ek traffic simulator bhi banayenge jo automatically normal aur abnormal traffic generate karega.**
>
> **Ye logs hamare cloud monitoring system mein jayenge. Backend unhe Amazon SQS queue mein dalega. Workers queue se logs uthakar process karenge. Raw logs S3 mein aur structured data RDS mein store hoga. Phir anomaly detection system check karega ki application ka behaviour normal hai ya nahi — jaise error rate suddenly badh gaya, API bahut slow ho gayi, traffic suddenly spike hua, ya failed login attempts unusual ho gaye.**
>
> **Agar kuch abnormal detect hota hai, system incident create karega aur dashboard par show karega. EC2 compute ke liye, S3 storage ke liye, SQS asynchronous processing ke liye, RDS database ke liye, IAM security/access control ke liye aur CloudWatch infrastructure monitoring ke liye use hoga.**

# 📌 49. Core Project Philosophy

The project follows one simple flow:

```text
BUILD A WEB SYSTEM
        ↓
GENERATE REALISTIC ACTIVITY
        ↓
COLLECT ITS LOGS
        ↓
PROCESS THEM IN THE CLOUD
        ↓
UNDERSTAND NORMAL BEHAVIOUR
        ↓
DETECT ABNORMAL BEHAVIOUR
        ↓
SHOW THE PROBLEM
```

The goal is not to build the biggest web application.

The goal is to demonstrate how a **real cloud-based monitoring architecture** can observe and analyze the behaviour of a web system.
